## 一、致命

### BUG-输入-01 连击会「丢键」：收招的 0.16 秒里按下的攻击被彻底吃掉
- 玩家视角：玩家连按 `F` 想打三连击。前两下很顺，第三下**没出来**，角色站着发愣，再按一下才动。玩家读到的是「连击不跟手 / 有时按了没反应」。
- 位置：`index.html:1608-1616` `updatePlayer`
  ```js
  1608:  if(inp.atk && canAct && p.swingCd<=0){
  ...
  1614:  } else if(inp.atk && p.swingT>0){
  1615:    p.swingQueued = true;
  1616:  }
  ```
- 根因：`inp.atk` 是**边沿量**——键盘走 `keyPressed()`（`index.html:769`，取走即清 `_p`），手柄走 `padEdge()`（`index.html:652`，置 `padPrev`）。分支只覆盖两种状态：
  - `p.swingCd > 0`（上一段收招的 0.16 秒，`index.html:1639` `p.swingCd = 0.16;`）→ 第一个条件假；
  - `p.swingT <= 0`（已经收完）→ 第二个条件也假。

  两个都不成立时，**这次边沿已经被 `keyPressed` / `padEdge` 消费掉，永远不会再来一次**。0.16 秒在 60fps 下是 9~10 帧，玩家「稍快一点」就掉进去。三连击的手感问题主要来自这里。
- 修改方案：把「收招窗口内按下的攻击」也记进队列，别丢。在 `1614` 的 `else if` **之前**插一条：
  ```js
  if(inp.atk && p.swingT<=0 && p.swingCd>0){
    p.swingQueued = true;          /* 收招窗口内的输入记下来，别吃 */
  } else if(inp.atk && p.swingT>0){
    p.swingQueued = true;
  }
  ```
  注意 `1639` 那一行收招时会把 `p.swingQueued = false`（`1636` 附近）——要保证「收招窗口内记下的 queued」能活到下一次 `swingT>0` 的开招，否则照样丢。更稳的做法是把 `p.swingCd` 从 0.16 降到 0.08，并把 `swingQueued` 改成时间戳缓冲（`p.atkBufT`，0.12 秒内有效）。建议先做前一条（改动最小），A/B 对比手感后再决定要不要上缓冲队列。
- 验证判据：写 3 行脚本按固定 180ms 间隔发 `keydown`/`keyup`（`KeyF`），统计 `p.swingIdx` 到达 2 的次数；改前应能看到大量只到 1 就停。
- 严重度：**致命**

### BUG-输入-02 `Ctrl+R` / `Cmd+R` 会先重开游戏再刷新页面
- 玩家视角：玩家在暂停页按 `Ctrl+R` 想刷新（改完代码重载），结果**游戏先重开了一次**、然后浏览器才刷新。偶尔还会因为 `startGame()` 里的 `playIntro()` 与页面卸载竞争，黑屏闪一下。
- 位置：`index.html:1108` `updatePaused`
  ```js
  1108:  if(keyPressed(["KeyR"])){ startGame(); return; }
  ```
- 根因：`keyPressed`（`index.html:769`）只看 `KEYS[code+"_p"]`，不查 `ctrlKey` / `metaKey` / `altKey`。而同一个项目里 `js/audio.js` 的 `M` 键处理**是查了**修饰键的（`if (e.code === "KeyM" && !e.ctrlKey && !e.metaKey)`）—— 一个项目两种写法。全文 grep `ctrlKey|metaKey|altKey` 在 `index.html` 里 **0 命中**。
- 修改方案：在 `keydown` 监听器（`index.html:586`）开头加一道修饰键过滤，放在 `587` 之后、`588` 之前：
  ```js
  if(e.ctrlKey || e.metaKey || e.altKey) return;   /* 浏览器快捷键原样放行，别抢 */
  ```
  这一行同时解决 `Cmd+A` 全选被 P1 的 `KeyA`（左移）吃掉、`Alt+Tab` 后 `Alt` 仍被当成按着的问题。
  副作用检查：项目里没有任何 `Ctrl+` 组合键是游戏功能，所以这道过滤不会挡掉任何玩法输入。
- 严重度：**致命**（现场演示时改代码重载是高频动作，每次都会先丢一局进度）

### BUG-输入-03 `blur` 只清短片计时，不清按键状态 —— 切回来「角色自己一直往右走」
- 玩家视角：玩家按住 `D` 往右跑，中途 `Alt+Tab` 去看攻略，回来点一下画面 —— **角色还在往右跑**，明明手已经松开了。得再按一下 `D` 再松开才能停。
- 位置：`index.html:634-639`
  ```js
  634:  /* 失焦 / 切标签页：键位状态全清，否则会一直以为玩家按着跳过键 */
  635:  window.addEventListener("blur", function(){
  636:    introKeyDownAt = 0;
  637:    introHoldT = 0;
  638:    introSetHoldUI(false, 0);
  639:  });
  ```
- 根因：注释写的是「键位状态全清」，但**实际只清了短片的三个变量**。`KEYS`（`index.html:585`）与 `KEYS[*_p]` 完全没动。切走时按着 `D`，`keyup` 永远不会到达（焦点已失），于是 `KEYS["KeyD"]` 恒为 `true`，`keyDown(["KeyA"])` 里的 `keyDown` 一路读下去 → 一直右移。
  同一类问题还有两处：
  - `G.paused` 时 `clearPressed()`（`index.html:1075`）只清 `_p` 标记，不清 `KEYS` 本体 —— 对，这是故意的（移动要保留）；但 `blur` 时连 `_p` 都没清。
  - `startGame()`（`index.html:894`）**没有** `clearPressed()`，所以从失败页按 `R` 重开时，`R` 的 `_p` 标记还留着（虽然 `R` 不是动作键，但同一次按键的其它键可能也还在）。
- 修改方案：`blur` 里补全清：
  ```js
  window.addEventListener("blur", function(){
    introKeyDownAt = 0;
    introHoldT = 0;
    introSetHoldUI(false, 0);
    for(var k in KEYS){ KEYS[k] = false; }      /* 含 _p 标记，一次清干净 */
    if(window.Touch && Touch.clearAll) Touch.clearAll();
    if(G && G.paused === false && G.phase === "play") G.resumeGrace = 0.18;
  });
  ```
  `G.resumeGrace = 0.18` 这一句是关键：切回来时玩家手指往往正按着某个键（点回窗口的那一下），不设闸会顺手挥一刀 —— 与 `togglePause` 解冻时同一套处理（`index.html:1056`）。
  另外建议把 `Touch.clearAll()` 从 `js/touch.js` 自己的 `blur`/`pagehide` 监听里保留（它已经做了，`js/touch.js:916,919`），这里只是让键盘也享受同样的待遇。
- 验证判据：按住 `D` → 触发 `window.blur` → 松开 → `focus`。`KEYS["KeyD"]` 必须为 `false`，角色不得继续移动。
- 严重度：**致命**

### BUG-输入-07 粒子没有上限，最坏一帧能堆到上千个 `fillRect`

- 位置：`index.html:1457-1465` `burst`；`index.html:3655-3663` `drawParticles`
  ```js
  1457: function burst(x,y,n,col,spd){
  1458:   for(var i=0;i<n;i++){
  1459:     var a = rnd(0,Math.PI*2), s = rnd(spd*0.25,spd);

  function burst(x,y,n,col,spd){
    var room = PARTICLE_CAP - G.particles.length;
    if(room <= 0) return;
    if(n > room) n = room;
    ...
  ```
  再配一条更省的：`drawParticles` 按 `col` 分组，每组只设一次 `fillStyle` —— 能把 `fillStyle` 赋值从 1260 降到 ≤ 8（`fillRect` 本身没法批量，但属性赋值是纯 JS 开销，同样值得省）。
- 严重度：**高**

| 5 | **游戏画面区没有独立的 `touch-action`**：只有 `html,body` 上有（`index.html:19`），`#stage` 没有 | 在画面上双指仍可能触发浏览器缩放（部分 ROM 会忽略 body 的 `touch-action`） | `#stage{touch-action:none}` 补一条（`#tch-layer` 自己已有，`js/touch.js:136`） |
| 6 | **没有游戏事件的触觉反馈** | `Touch.buzz` 只在按键时 8ms（`js/touch.js:516` 附近）；命中 / 受击 / 死亡 / 破阵全都没有触感 | 在 `hitEnemy` / 受击 / `goWin` / `gameOver` 里调 `Touch.buzz(...)`，与 `Rumble` 预设一一对应（`hit:12ms`、`hurt:30ms`、`die:[40,60,40]`） |
| 7 | **手柄与触屏无法共存**：`active()` 里 `Guide.padCount() > 0` 就隐藏虚拟键（`js/touch.js:767`） | 插着手柄但想用触屏的人没路 | 改成「手柄真的动过才隐藏」（读 `Guide.device() === "pad"`），或顶栏加一枚「切换输入」小键 |
| 8 | **没有横屏锁定** | 转成竖屏才看到「请横过来」（`tch-portrait`），但此时游戏已在跑、按键已错位 | `screen.orientation.lock("landscape")`（需全屏），失败时保留现有遮罩并在遮罩上加「全屏」按钮 |
| 9 | **没有「按住连发」**：`Touch.state()` 是边沿语义（`js/touch.js:733-734` 取走即清） | 打三连击必须快速点三次；拇指在 0.4s 内连点 3 次很难 | 给 `atk` / `act` 加「按住 120ms 后按 160ms 间隔自动重发 edge」的连发器，移动与跳不开 |

## 八、最严重 3 条（摘要）

1. **BUG-输入-01（致命）连击在收招窗口丢键** —— 0.16 秒内按下的攻击被 `keyPressed` / `padEdge` 消费后永不重放，三连击打不出来。一句话修：`index.html:1608` 前补一条「收招窗口内也记 `swingQueued`」。这是唯一一条直接破坏核心战斗手感的缺陷。
2. **BUG-输入-03（致命）`blur` 不清按键状态** —— 切窗口回来角色自己一直走，必须再按一下同方向键才能停。注释写着「键位状态全清」但实际只清了短片的三个变量，是典型的「注释与代码脱节」。
3. **BUG-输入-02（致命）`Ctrl+R` 会先重开游戏再刷新** —— 全文 `index.html` 对 `ctrlKey`/`metaKey`/`altKey` **零处理**，而 `js/audio.js` 的 M 键处理是查了的。一行过滤即可，但影响每一次改代码重载。
