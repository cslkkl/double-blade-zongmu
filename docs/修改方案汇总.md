## 二、已驳回（5 条，附实测反证）

审计结论不等于事实，以下五条我用数据推翻了，**不改**：

### 1. 画面-03「11 把武器的 attack 帧全都长得一样」

审计说折叠掉了重击/突刺的差异。实测：逐对量剪影差异（alpha>24 归一化后逐像素比），
**55 对里最小的是 hammer vs spear 12.1%**，最大 sword vs bow 46.2%，全部 >8% 合格线。

→ 每把武器的出招动作本来就不同，`char-rig.js` 把 attack 族折叠成武器的 `attack` 档
是正确设计（注释也写明「重击/突刺的差异在武器自己的 4 帧里」）。
`attack-heavy/thrust` 那 8 张确实是死素材，但删它们不影响观感。

### 2. 画面-04「挥砍只播 1 帧」

实测按真实 `swingDur=0.2s`、60fps 复算 `attackFrame` 的帧分布：
帧 0 出现 4 次、帧 1/2/3 各 3 次，**4 帧全部上屏**。每帧 50~67ms 在 0.2 秒挥砍里是正常密度。

### 3. 画面-02 的 `pickup` 部分「偏小 1.1%~17.5%，应一并归一化」

实测反驳：`pickup` 是**弯腰**，宽高比从 walk 的 2.19 掉到 1.19（身体横向铺开）。
按包围盒高归一化会把弯腰的人放大到站立高度 —— 那是新 bug。
逐张量「身体主体高 / 画布高」：pickup 0.74~0.81 vs walk 0.83~0.95，差 10~15%
正是弯腰的正常幅度。只有 `spear` 是 0.889 > 0.864（反了），已单独修。

### 4. 画面-07「58% 的帧超出验收带」

逐张量「身体主体高 / 画布高」（15% 宽度阈值排除武器尖端）后：
`jump` 133.6px 是蹲姿、`pickup` 162.9px 是弯腰、`hurt` 174.9 / `bow` 175.9 在容差内、
`dead` 183.1 只在结算页出现。真正要改的只有 `attack`（184.3），已修。

顺带核实 `walk` 的 `scaleFix=1.49` 为何这么高：walk 帧 bbox 是 (246,260,406,498)，
内容只占画布下半部（身体高 238 / 画布 498 = 0.478），1.49 正是把矮小的原画放大到 179.4px。
**这是设计，不是抄错数。**

### 5. 输入-08「每帧 18 个 Gradient」

实测满负载（7 敌 + 400 粒子）是 **31 个/帧**，比审计估的更多。但：
这些 Gradient 全在**纯代码降级路径**里（素材缺失时才走），正常运行几乎不触发；
且满负载 render 总共 0.85ms（16ms 预算的 5%）。**没有优化必要。**

## 四、审计方法上的三条结论（写下来给下一个人）

1. **自检全绿 ≠ 画面对。** `walk-axe-3` 缺失、4 帧退化 3 帧时，`selftest_weapons` 依然 0 失败；
   挥砍 4 帧只播 1 帧时也全绿（断言门槛 `seen.size >= 2` 太低）。
   身高、锚点、步频、体积这四类问题全都能在 0 失败前提下存在。
2. **审计员的结论也要复核。** 本次 5 条被实测推翻（见第二节），其中 3 条是因为
   「用包围盒高当身高」这个口径错误 —— 蹲姿、弯腰、举武器时包围盒不等于身高。
   `AGENTS.md` 的活跃坑里早就记过这个坑，审计时没读到。
3. **行号会漂。** `index.html` 一天内从 4165 涨到 4335 行。所有引用都要按
   「函数名 + 原文片段」定位，报告里附行号只是方便当时阅读。
