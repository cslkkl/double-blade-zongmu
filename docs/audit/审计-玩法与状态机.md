## 一、确认的玩法 / 状态机缺陷

### BUG-玩法-01 手柄玩家在对局里根本按不出暂停

- 玩家视角：插着手柄从头打到尾，想暂停去倒杯水。按 Start —— 没反应；按 Back —— 抽屉不开（抽屉只在 ui-shell 的覆盖层分支里认 Back）；按 A / B / X / Y —— 全在打人、跳、放技能、捡东西。只能放下手柄去摸键盘按 Esc，或者去点屏幕上的小条。而暂停页上明明写着「Start 继续」，指南图例也明写「Start 暂停」。
- 位置：`index.html:686 readPad(p, tag)`。返回对象里只有 `left / right / jump / atk / skill / act / drop / give`，**没有 pause 字段**：

  ```js
  return {
    left: ax < -0.42 || btn(14),
    right: ax > 0.42 || btn(15),
    atk:  padEdge(tag+"_a", btn(0)),
    jump: padEdge(tag+"_x", btn(2)),
    skill: padEdge(tag+"_b", btn(1)),
    act:   padEdge(tag+"_y", btn(3)),
    drop:    padEdge(tag+"_ddown", btn(13)),
    give:    padEdge(tag+"_dup",   btn(12))
  };
  ```

  全局 `togglePause` 的调用点只有四处：`index.html:632`（Esc 的 keydown）、`index.html:1135`（暂停页里「继续」）、`index.html:1419`（`#btnResume` 点击）、`js/touch.js:661`（触屏 ❚❚）。**没有一处读手柄 Start**。`btn(9)` 只在 `updatePaused`（`index.html:1134`）里出现，那是已经暂停之后用来「继续」的。
- 根因：暂停是后加的能力，只补了键盘（Esc）与触屏（虚拟键）两条腿。`readPad()` 的字段表在暂停功能落地前就定死了，后来没人往里加 `pause`。这与 `AGENTS.md`「活跃坑」里那条「`readPad()` 只在 `play` 阶段被调用，离开对局就没人读手柄」是同一个坑的另一半 —— 那次修的是「覆盖层上读不到手柄」，这次是「对局中读不到 Start」。
- 修改方案：三步，都不动现有字段语义。
  1. `index.html:703` 之后（`give` 那行后面）加一行：
     ```js
     pause: padEdge(tag+"_start", btn(9)),   /* Start 暂停 */
     ```
     同时把 `index.html:687` 那个全 false 的默认返回对象补上 `pause:false`（`if(!p) return {...}` 那一行），否则没插手柄时 `inp.pause` 是 `undefined`。
  2. `index.html:2501`（`in1` 组装）加 `pause: pad1.pause || false,`，`index.html:2513`（`in2`）加 `pause: pad2.pause || false,`。
  3. 在 `update()` 的 play 分支里，`updatePlayer` 之前（`index.html:2532` 上方）加：
     ```js
     if(in1.pause || (in2 && in2.pause)){ togglePause(true); return; }
     ```
     `return` 是必须的：暂停后这一帧不该再跑模拟。注意别放进 `resumeGrace` 那段清零里（`index.html:2524`），暂停键不该被 0.18 秒沉默吃掉。
- 影响面：只新增一个字段 + 一个早退分支，`readPad` 的其它键与 `padEdge` 前缀（`p1_start` / `p2_start`）不与现有任何 tag 冲突。两人各一把手柄时两人都能暂停；共用一把时 `PADS[1]` 为空，`pad2` 恒 false，行为正确。要顺带确认 `stopPadEdge()`（`index.html:1111`）在进暂停时清 `padPrev`，否则 Start 的边沿会漏进暂停页 —— 现在 `togglePause(true)` 里已经调了（`index.html:1066` 附近），够用。
- 严重度：**高**。手柄是这游戏对外宣传的主操作方式（指南、录屏说明、`PAD_LEGEND` 全部以手柄为主），主操作方式没有暂停键，是功能缺口而不是手感问题。

### BUG-玩法-02 打队友会把他的稀有武器换成一把更烂的玉璋刃

- 玩家视角：双人局，队友刚在 BOSS 身上捡到紫色光晕的神树锤（或神鸟弓），正开心。你一刀砍过去想帮他打身后的敌人，刀锋扫到了他 —— 屏幕上飘「武器脱手！」，他手上变成玉璋刃，锤子掉在地上。他弯腰去捡，30 秒后如果没捡回来，锤子就没了。更难受的是：换上的玉璋刃耐久只有 40，比开局那把（表里 `dur:55`）还短，看着是同一把刀却更快碎。
- 位置：`index.html:2272 doSwingHit(p, other)` 的友伤段，`index.html:2298–2307`：

  ```js
  if(other && !other.dead && p.hitSet.indexOf(other) === -1){
    if(rectHit(box, other.rect())){
      p.hitSet.push(other);
      other.vx = p.facing * 520;
      other.vy = -300; other.onGround = false;
      other.hurtT = 0.2;
      if(other.weapon && other.weapon.key !== "short"){
        dropWeapon(other.x, other.y, other.weapon);
        other.weapon = newWeapon("short");
        other.weapon.dur = 40;              /* ← 表里 short 的 dur 是 55 */
        ...
        showHitText(other.x, other.y-170, "武器脱手！");
  ```

  对照武器表 `index.html:718`：`short: { name:"玉璋刃", type:"melee", dmg:2, dur:55, ... }`。
- 根因：这段是「打队友不扣血，但震掉武器」的惩罚设计，写的时候为了让「换上的刀别太耐用」硬写了一个 40，绕过了 `newWeapon()` 从表里取 `dur` 的正规路径。两个后果叠在一起：① 惩罚落在**稀有武器**上（`key !== "short"` 才触发，正好把 bow / hammer / sword 全包括），收益最低的玩家吃最重的惩罚；② 换来的替代品比表里同款更差，玩家会读成「被队友坑了还被系统再坑一次」。
- 修改方案：改 `index.html:2307` 一行，让它回到表里：
  ```js
  other.weapon.dur = other.weapon.max;      /* 与 newWeapon 一致，别硬写 40 */
  ```
  如果设计上确实要「临时惩罚」，就把它写成语义明确的常数并在 `WEAPONS` 附近声明（例如 `var DISARM_DUR = 40;`），不要留一个和表冲突的魔法数。另外建议把 `key !== "short"` 判据换成「只震落近战重武器 / 稀有货」以外的口径（例如只对 `isRareWeapon` 生效），否则队友刚捡到青铜剑也会被震掉，双人配合的乐趣被这条惩罚压住了。
- 影响面：只影响友伤分支里那把替代武器的耐久；`dropWeapon` 落地的原武器仍按 `DROP_LIFE = 30`（`index.html:421`）计时，不变。改完要回归一次「队友捡回原武器后耐久是满的」——`dropWeapon` 传的是 `other.weapon` 原对象，耐久没被改，捡回来是对的。
- 严重度：**高**。这是玩家会明确读成「我被自己人坑了」的场景，且惩罚不可逆（30 秒后掉落物消失）。

### BUG-玩法-03 「机关咬合 · 下一阵提前」是句空话：喘息期激活 rush 机关没有任何效果

- 玩家视角：第二阵 / 第四阵末尾，场上只剩一两个残兵，屏幕右上浮出「青铜机关 · 就在近处」，一台机关立在身侧。你跑过去按 Y，屏幕炸开金光、飘字「机关咬合 · 下一阵提前」，还配了一记闷震和锯齿音。然后你等着下一阵提前压上来 —— 结果还是老老实实等了整整 3 秒喘息。下一次开局机关又变回未激活的样子（换了新的一台），你会怀疑自己上次是不是没按对。
- 位置：三处联动。
  - `index.html:1000 waveCleared()`：喘息时长在这里**一次性算定**，`index.html:1007`：
    ```js
    G.breatherT = G.mechSkipBreather ? 0.5 : BREATHER;
    ```
  - `index.html:2017 activateMechanism(m, p)`，`index.html:2026`：
    ```js
    if(m.mode === "rush"){
      G.mechSkipBreather = true;
      showHitText(m.x, m.y-220, "机关咬合 · 下一阵提前");
    ```
  - `index.html:962 startWave(i)`，`index.html:968`：`G.mechSkipBreather = false;`
  - 机关浮出的时机 `index.html:2563`：
    ```js
    if(!G.mechSpawned && G.spawnQueue.length === 0 && alive <= 2 && G.waves[G.waveIdx] && G.waves[G.waveIdx].mech){
    ```
- 根因：`mechSkipBreather` 是「被消费一次就作废」的标记，但**消费点在时间上早于写入点**。机关只在「刷怪队列排空、场上剩 ≤2 个」时浮出 —— 此刻清场判定（`index.html:2598`，要求 `G.enemies.length === 0`）还没触发，玩家需要几百毫秒跑过去按 Y；而残兵往往在这段路里被打死，`waveCleared()` 先跑，按当时 `mechSkipBreather === false` 把 `breatherT` 定成 3.0。玩家随后按下 Y，标记才置 true，但 `breatherT` 已经定了，没有任何代码重算；再往后 `startWave()` 把它重置回 false，标记彻底丢失。结果就是提示文案与数值各说各话。
- 修改方案：在 `activateMechanism` 的 rush 分支里**直接把当前喘息压短**，而不是留一个标记等下一次读取。改 `index.html:2026` 那一行：

  ```js
  if(m.mode === "rush"){
    G.mechSkipBreather = true;                 /* 保留：万一这阵还没清场 */
    G.breatherT = Math.min(G.breatherT, 0.5);  /* 新增：喘息已开始也能立刻生效 */
    showHitText(m.x, m.y-220, "机关咬合 · 下一阵提前");
  ```

  `Math.min` 而不是直接赋值：如果玩家是在喘息最后 0.2 秒按的，不该被「压到 0.5」反而变长。`breatherT === 0`（还没清场）时 `Math.min(0, 0.5) = 0`，不改变行为，标记仍然管用。
- 影响面：只改 rush 分支的数值结算。`waveCleared()` 的 `mechSkipBreather` 读取路径保留，所以「先按机关、后清场」这条时序仍然生效。要回归：heal 机关（回满血）走的是 `else` 分支，不受影响；`G.breatherT` 被外部读的地方只有喘息倒计时（`index.html:2586`）与 `waveCleared` 的防重入（`index.html:1002`），压到 0.5 不会让 `waveCleared` 二次触发。
- 严重度：**高**。提示文案直接对玩家说谎，且这条机关是第 2、4 阵唯一的「节奏奖励」，失效等于这两阵少了一个设计要素。

### BUG-玩法-04 换阵的瞬间，没开的宝箱凭空消失

- 玩家视角：上一阵清完，喘息 3 秒，两台宝箱落在身侧。你正走过去、手指已经放在 Y 上，3 秒到 —— 宝箱「啵」一下没了，原地换成两台新的（新落点），旧的连个消失特效都没有。如果你动作慢一点，永远开不到前一阵的箱子；如果你动作快，也只能开一台（另一台被新的挤掉位置感）。
- 位置：`index.html:1015 nextWave()`，`index.html:1022`：

  ```js
  G.chests = [];
  var base = G.p1 ? G.p1.x : 560;
  addChest(base + 360, G.waveIdx);
  addChest(base - 480, G.waveIdx);
  ```
- 根因：`G.chests = []` 在摆新箱子之前无条件清空，把「破阵奖励」当成「开局摆设」处理。注释（`index.html:1018–1021`）写的是「先清上一轮的残箱再摆」，意图是防堆积，但没考虑玩家还没开。同时 `nextWave()` 由喘息倒计时自动触发（`index.html:2590`），玩家没有「准备好了」的按钮，所以这是一次玩家无法阻止的没收。
- 修改方案：只清**已开过**的，保留未开的。改 `index.html:1022` 为：

  ```js
  /* 只收走已经开过的空箱；没开的留给玩家，别在喘息结束那一帧没收 */
  G.chests = G.chests.filter(function(c){ return !c.opened; });
  ```

  若担心跨阵堆积，可加一个上限（例如 `if(G.chests.length > 4) G.chests = G.chests.slice(-4);`）。另一条更彻底的方案：把喘息改成「玩家按继续键才进下一阵」（`#btnNext` 与 `ovClear` 本来就在 DOM 里，见 BUG-08），但那是设计变更，不建议在修 bug 的批次里做。
- 影响面：`G.chests` 的读者有 `tryOpenInteract`（`index.html:1945` 起）、`nearestInteract`（`index.html:2038` 起）、`drawChests`（`index.html:3777`）。`filter` 返回新数组，不影响这三处的遍历语义。`startGame`（`index.html:940`）仍然整体清空，重开一局不会残留。要注意：保留旧箱会让同屏宝箱数从 2 涨到最多 4~6，`drawChests` 没有数量上限，画面会挤 —— 所以建议同时加上面那条 4 台上限。
- 严重度：**中**。玩家会明确感到「奖励被没收」，但不是每局必现（动作快的玩家碰不到）。

### BUG-玩法-05 宝箱落点跟着玩家脚下算，会落到画面外，且没有任何指引

- 玩家视角：你贴着屏幕左边缘清完场，喘息开始。新的一阵开始，屏幕上没有任何宝箱；你往前走了一段才在身后发现一台（或者干脆整局没找到）。另一头也一样：贴着右边缘时，落在 `base + 360` 的箱子在屏幕右侧外面。
- 位置：`index.html:1015 nextWave()` 的落点计算（`index.html:1023–1025`）与 `index.html:1931 addChest(x, waveIdx)` 的夹取：

  ```js
  var base = G.p1 ? G.p1.x : 560;
  addChest(base + 360, G.waveIdx);
  addChest(base - 480, G.waveIdx);
  ...
  function addChest(x, waveIdx){
    G.chests.push({
      x: clamp(x, 140, WORLD_W-140), y: GROUND, ...
  ```
- 根因：落点用「玩家世界坐标 ± 固定偏移」，夹取范围却是**整个世界**（140 ~ `WORLD_W-140` = 3260），不是**当前画面**（`G.camX ~ G.camX + W`）。而玩家被限制在画面内（`index.html:2583`：`p.x = clamp(p.x, G.camX+54, G.camX+W-54)`），所以 `base - 480` 完全可能 < `G.camX`（玩家贴左边时 `base ≈ camX+54`，减 480 后是 `camX - 426`）。此时箱子在世界里合法、在画面外，玩家看不见，也没有小地图或箭头提示。
- 修改方案：把夹取基准从「世界」换成「当前画面」，并保证两台箱子分居玩家两侧但都在屏内。改 `index.html:1023–1025` 为：

  ```js
  var base = G.p1 ? G.p1.x : 560;
  var lo = G.camX + 160, hi = G.camX + W - 160;      /* 画面内留边距 */
  addChest(clamp(base + 360, lo, hi), G.waveIdx);
  addChest(clamp(base - 480, lo, hi), G.waveIdx);
  ```

  `addChest` 里那层 `clamp(x, 140, WORLD_W-140)` 保留当兜底（画面可能贴世界边界）。若担心两台夹到同一侧，可对第二台做「若与第一台距离 < 240 则翻到另一侧」的处理。
- 影响面：只改落点。`addChest` 的 `y` 恒为 `GROUND`，不受影响；`tryOpenInteract` / `nearestInteract` 的判定半径（`INTERACT_R`，`index.html:418`）与位置无关，不用改。
- 严重度：**中**。不是每局必现（取决于清场时玩家站在哪），但一旦撞上就是「这一阵的奖励我压根没看见」。

### BUG-玩法-06 气泡说「按 Y 拾取」，按了却没反应：提示半径 90 与判定半径 80 不一致

- 玩家视角：地上躺着一把武器，你走过去，屏幕上浮出「按 Y 拾取 · 青铜剑」。你按 Y —— 什么都不发生，气泡还在。再走一小步、再按，才捡起来。同样的距离，开宝箱却是按一下就行（宝箱判定是 150 的纵向带宽，武器是 140）。
- 位置：三组半径各说各话。
  - 提示判定 `index.html:2093 nearestDrop(p, blocked)`，`index.html:2100`：`if(!(dx < HINT_RANGE.x && dy < HINT_RANGE.y)) continue;`，`HINT_RANGE = { x: 90, y: 140 }`（`index.html:2088`）。
  - 实际拾取 `index.html:1839 tryPickup(p)`，`index.html:1843`：`if(Math.abs(d.x - p.x) < 80 && Math.abs(d.y - p.y) < 140){` —— 硬编码 80 / 140。
  - 声明了但**没有任何读者**的 `index.html:2087`：`var PICK_RANGE = { x: 80, y: 140 };`（注释还写着「与 tryPickup 一致」，但它自己没被用）。
- 根因：`HINT_RANGE` 比实际拾取宽 10px 是故意的（「提示早一点出来，玩家不用贴脸」），但宽出来的那一圈没有对应的「按了也白按」的反馈，于是变成骗人带。同时 `PICK_RANGE` 是个没接线的抽象，本该让两处共用同一组数字，结果 `tryPickup` 继续硬编码。
- 修改方案：两件事。
  1. `index.html:1843` 改成读 `PICK_RANGE`：
     ```js
     if(Math.abs(d.x - p.x) < PICK_RANGE.x && Math.abs(d.y - p.y) < PICK_RANGE.y){
     ```
  2. 消掉骗人带。最省事的做法是把 `HINT_RANGE.x` 收到与 `PICK_RANGE.x` 相等（`index.html:2088` 改成 `{ x: 80, y: 140 }`）；想保留「早提示」就把提示文案分档：`dx` 在 `PICK_RANGE.x` 之外时显示「走近一点 · 青铜剑」而不是「按 Y 拾取」。后者要多一次 `nearestDrop` 的距离回传，改动稍大，本次建议先做前者。
  3. 顺手把 `INTERACT_R`（`index.html:418`，`{x:80,y:150}`）的纵向 150 与武器的 140 对齐，或者把三组半径合并成一张表（`PICK_RANGE` / `HINT_RANGE` / `INTERACT_R`），避免以后再漂。
- 影响面：`nearestDrop` 同时被 `updatePickupHint`（`index.html:2120`）用于「同款武器，先扔掉」的 blocked 分支，收窄 10px 只影响气泡出现时机，不影响拾取本身。`tryPickup` 改成读常量后行为完全等价（数值没变）。
- 严重度：**中**。10px 在 1600 宽的画面里约 0.6% 屏宽，但拾取是每局几十次的高频动作，撞上概率不低。

### BUG-玩法-07 机关从不清场，跨阵累积；已激活的机关还一直立在原地

- 玩家视角：打到第四阵，地图上已经立着三台青铜机关，其中两台是上一阵、上上阵激活过的（金光亮着，走过去按 Y 完全没反应，因为 `tryOpenInteract` 只认 `!o.on`）。它们不消失、不变化，纯占地方，还会把新机关往远处挤 —— 新的那台有时被推到很偏的位置，你要跑很久才能按到。
- 位置：`G.mechanisms` 只在 `startGame` 里清（`index.html:940`：`G.chests = []; G.mechanisms = []; G.pickups = [];`），`nextWave()`（`index.html:1015`）**不清**。新机关落点避让见 `index.html:2568–2569`：

  ```js
  for(var mc=0; mc<G.mechanisms.length; mc++){
    if(Math.abs(G.mechanisms[mc].x - mx) < 180) mx = clamp(mx + 320, 160, WORLD_W-160);
  }
  ```
- 根因：`G.chests` 每阵重置，`G.mechanisms` 没有对应的重置，只有开局清空。避让循环又是「每撞一台就 +320」，累积到第三、第四台时 `mx` 会被推得很远（而且 `clamp` 到右边界后可能反复落在同一处，避让失效）。已激活的机关保留在数组里也是这个原因 —— 没有清理时机，`drawMechanisms`（`index.html:3889`）就照旧画 `mechanismOn`。
- 修改方案：两处小改。
  1. `nextWave()` 里加一行清掉已激活的（放在 `G.chests` 那行旁边，`index.html:1022` 附近）：
     ```js
     G.mechanisms = G.mechanisms.filter(function(m){ return !m.on; });
     ```
     与 BUG-04 同一套口径：只收走用掉的，留下玩家还没按的。
  2. `index.html:2568–2569` 的避让改成「找到一个不撞的落点就停」，别每撞一台就继续推：
     ```js
     for(var tries = 0; tries < 4; tries++){
       var clash = false;
       for(var mc=0; mc<G.mechanisms.length; mc++){
         if(Math.abs(G.mechanisms[mc].x - mx) < 180){ clash = true; break; }
       }
       if(!clash) break;
       mx = clamp(mx + 320, 160, WORLD_W-160);
     }
     ```
- 影响面：`G.mechanisms` 的读者是 `tryOpenInteract`（`index.html:1945` 起，跳过 `on`）、`nearestInteract`（`index.html:2038` 起，跳过 `on`）、`drawMechanisms`。过滤掉 `on` 的项后这三处的行为不变（它们本来就跳过 `on`），只是画面干净了、避让准了。`startGame` 的整体清空保留。
- 严重度：**中**。不影响胜负，但「按了没反应的金光机关」会被读成 bug，而且机关是新机关被推远，直接影响 rush / heal 的可达性。

### BUG-玩法-08 `phase === "clear"` 是一条死分支，`#ovClear` 与「继续 →」按钮永远走不到

- 玩家视角：（玩家看不到，但这是同一个坑的另一面）`index.html` 里有一整套「这一阵守住了 / 继续 →」的过关页，DOM（`index.html:332–338`）、样式、`#btnNext` 的点击处理（`index.html:1414`）全在，但正常流程里它永远不会出现。玩家只会看到「喘息」横幅。如果将来有人把喘息改成「按继续」，这套东西才会活过来 —— 而现在它是**只能靠鼠标点**的死页面。
- 位置：`index.html:2615–2622` 的结算分支：

  ```js
  confirmT += dt;
  if(confirmT >= CONFIRM_ARM && (padConfirmEdge() || kbConfirmEdge() || touchConfirmEdge())){
    if(G.phase === "lose" || G.phase === "win") restartAll();
    else if(G.phase === "clear") nextWave();
  }
  ```
  `G.phase` 的取值集合是 `title / play / win / lose`（`index.html:947` 起写 `"play"`，`index.html:1031` 写 `"win"`，`index.html:1039` 写 `"lose"`），**没有任何地方写 `"clear"`**。`showOv("ovClear")` 也从未被调用（`showOv` 的三处调用是 `ovWin` / `ovLose` / `ovPause`）。
- 根因：过关流程从「弹过关页 → 玩家点继续」改成了「3 秒喘息自动进下一阵」（见 `index.html:1005–1006` 的注释），但旧分支与旧 DOM 没删。`OVS` 数组（`index.html:1158`）里还留着 `ovClear`，`hideOv()` 每帧照样去 `classList.remove("on")` 一个永不 `on` 的元素。
- 修改方案：二选一，别留半截。
  - 若确认「喘息自动推进」是最终设计：删掉 `index.html:2621` 的 `else if(G.phase === "clear") nextWave();`，从 `OVS`（`index.html:1158`）里去掉 `"ovClear"`，并删掉 `#ovClear` 那段 DOM（`index.html:331–338`）与 `#btnNext` 的监听（`index.html:1414`）。
  - 若想保留「玩家自己按继续」的节奏（对双人局更友好，也顺手解决 BUG-04）：让 `waveCleared()` 设 `G.phase = "clear"` 并 `showOv("ovClear")`，`#btnNext` 的点击与 `padConfirmEdge` / `kbConfirmEdge` / `touchConfirmEdge` 三条腿都已有闸（`CONFIRM_ARM`，`index.html:1330`），是现成的。注意这条路要同时把喘息倒计时（`index.html:2586`）停掉，否则 3 秒后照样自动 `nextWave()`。
- 影响面：删分支影响面为零（不可达）。改成 `clear` 则影响 `update()` 的 phase 分支（`index.html:2596` 的 `title` / `else`）、`togglePause` 的 `phase !== "play"` 早退（`index.html:1068`）、以及 `anyPress` 那条标题路径 —— 改动面不小，建议本次只做「删死代码」。
- 严重度：**低**。玩家不直接受害，但它掩盖了「这一阵守住了」这条本该存在的反馈，也让 BUG-04 失去了一个更优雅的解法。

## 三、已修项本身的副作用（比新 bug 更值得看）

### SIDE-01 「收招窗口记 swingQueued」会攒出一次玩家没按的幽灵连击

- 现象：玩家在 0.16 秒收招窗口里多按了一下 A（这一下本来被吃掉），接着再正常按一下 A 出第一刀 —— 第一刀结束后会**自动**接第二刀，玩家根本没按第二下。如果他在窗口里按了却没再按，这个 `true` 会一直挂在 `p.swingQueued` 上，等下一次出刀后突然多挥一刀。
- 位置：置位在 `index.html:1711–1717`，消费在 `index.html:1728–1730`：
  ```js
  } else if(inp.atk && p.swingT<=0 && p.swingCd>0){
    p.swingQueued = true;        /* 置位 */
  ...
  if(p.swingQueued && p.swingIdx < 2){ p.swingQueued = false; startSwing(p, p.swingIdx+1); }
  ```
- 根因：消费逻辑只挂在 `if(p.swingT > 0)` 块内（`index.html:1721`）。收招窗口期间 `swingT <= 0`，所以这条路径置的位**当场没有消费者**；而 `swingCd` 归零后玩家再按 A，走的是第一个分支（`index.html:1703`）`startSwing(p, 0)`，它也不清 `swingQueued`。于是标记跨过一次出招，在那一刀结束时被当作「玩家要求接第二段」消费掉。
- 建议改法：让第一个分支显式清队列，把「这一下已经出招了」当作消费：
  ```js
  if(inp.atk && canAct && p.swingCd<=0){
    p.swingQueued = false;              /* 新增：新起手即清残留 */
    if(wpNow.type === "bow" || wpNow.type === "throw"){ ... } else { startSwing(p, 0); }
  ```
  另一种更贴原意的做法：把收招窗口那一支改成「若 `swingCd` 剩余不足 0.08 秒才记队列」，只吃「真的很接近下一刀」的输入。
- 严重度：**中**（相对原 bug 是「丢键」，现在变成「多键」，玩家读到的是「我按一下它自己连了两下」）。

### SIDE-02 旋风斩补的 `p.inv = 1.5` 会让角色全程半透明闪烁

- 现象：放旋风斩的 1.5 秒里，角色一直在闪（alpha 0.55 / 1 交替），因为 `js/char-rig.js` 把 `p.inv > 0` 直接当「受伤无敌闪烁」用：`p.inv > 0 && Math.floor(p.inv*20)%2===0` → `globalAlpha = 0.55`。玩家读到的是「我怎么一直在闪，是不是掉血了」。
- 建议改法：给无敌帧加来源标记，例如旋风斩时设 `p.invWhirl = 1.5`，`char-rig` 的闪烁判据改成 `p.inv > 0 && !p.invWhirl`；或在 `char-rig` 侧读 `p.whirlT > 0` 直接跳过闪烁（`pickClip` 已经优先判 `whirlT`，加一行同源判断最省事）。
- 严重度：**低**（观感问题，不影响判定）。

### SIDE-03 结算页闸未开时丢弃 `__confirmReq`，失败页刚出现时狂按无效

- 现象：两人同时倒下，玩家手还在 F 上连按，`kbConfirmEdge`（`index.html:1376–1381`）在闸未开时把请求**丢掉**，所以「一看到失败页就狂按」这一整段全部无效，必须松开再按一次。逻辑上安全（防误触），但和「按任意键继续」的肌肉记忆冲突。
- 建议：保留闸，但把「丢弃」改成「记住一次」（`KEYS.__confirmReq` 不清零，闸开了再消费一次）。因为 `showOv` 里已经 `resetConfirm()`（`index.html:1408`），不会跨页残留。
- 严重度：**低**。

## 四、可优化点（不是错误，是体验）

1. **`dropWeapon(x, y, wp)` 忽略 `y`**：`index.html:1876–1878` 恒用 `y: GROUND`、`vy: -420`。BOSS 在 `index.html:2365–2367` 传了 `e.y`（三件套 ±170 偏移），但都落在地面 —— 视觉上是从空中瞬移下去再弹一下。想让「空中掉的武器」落在空中，就得让 `y` 参与；不想的话建议把签名改成 `dropWeapon(x, wp)`，别留一个骗人的参数。
2. **`RESIDUE_LIFE` 注释与常量不符**：`leaveResidue` 附近的注释提到 18 秒，常量是 12（`index.html:422`）。以常量为准，改注释。
3. **`anyPress()` 没有启用闸**（`index.html:2627`）：读的是手柄按钮 **held**，页面加载时手柄 A 还按着，标题页会被当场跳过（`index.html:2612`）。模式页有闸，标题页没有。加一道「先见全松开」即可，与 `pzSeenUp` 同构。
4. **`introKeyDownAt` 只当布尔用**（`index.html:1197`、`1299`）：存了时间戳但只判 `> 0`，长按计时其实由 `introHoldT` 累加。删掉时间戳、换成布尔，或者真用它算时长（能顺带修「切标签页回来时按住时长被 blur 归零」）。
5. **`padIndexOf` 无调用方**（`index.html:1165`）：注释说「模块缺席时仍返回 0」，但 `Rumble.player` 内部已按 tag 分槽（`js/rumble.js:183–185`），这个函数是死代码。
6. **喘息期 `updatePickupHint` 仍在跑**（`index.html:2594`）：清场后场上只剩宝箱与掉落物，气泡其实有用，但 `nearestInteract` 会把已开宝箱跳过、未开的才提示 —— 与 BUG-04 一起看，若采纳「保留未开宝箱」，这条会自然变好。
7. **`if(!hitAny) return;`（`index.html:2320`）是空尾**：函数到此结束，这一行可删；留着会让后来的人以为后面还有代码。
8. **`G.mechSkipBreather` 的命名暗示「开关」，实际是「一次性标记」**：改名为 `mechRushRequested` 或按 BUG-03 的改法让它真正即时生效，别让命名继续骗人。
