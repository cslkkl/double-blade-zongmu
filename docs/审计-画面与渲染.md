### BUG-画面-01 拿青铜钺走路，第 4 帧永远是「第 3 帧的复制」，步态变成三段式

- **玩家看到**：捡起青铜钺往前走，角色只摆 3 个姿势就停住循环，走到第 4 步时**明显顿一下**——
  腿摆到一半突然跳回上一个姿势，节奏从「一二三四」变成「一二三、一二三」。
  对比同一角色空手走路（6 帧），持械走路反而更僵。
- **触发**：手上是 `axe`（青铜钺）时按方向键行走。
- **位置**：`js/anim-data.js:236`（`WEAPON_CLIP.axe.walk.files`）→
  `js/char-rig.js:888` `drawWalkFrames()` 的缺帧兜底 `js/char-rig.js:911-916`
- **根因**：`anim-data.js:230` 把 `assets/anim/walk-axe-3.webp` 当成第 4 帧登记进了 `files`，
  **但该文件在磁盘上不存在**（`git status` 显示 `D assets/anim/walk-axe-3.webp`，
  即工作区已被删除；HEAD 里它本来是有的）。`char-rig.js:911` 的 `imageOk()` 对
  不存在的文件返回 false（`img.complete` 在 404 后为 true 但 `naturalWidth === 0`），
  于是走 `911-921` 的「找同序列里最近的可用帧」兜底，
  而它只往前找（`(idx - k + n) % n`），所以第 4 帧**永远落到第 3 帧**（`walk-axe-2.webp`）。
  > 修订说明：本报告初稿记为「0 字节空文件」。复核 `git ls-files` + 全仓扫 0 字节文件后确认
  > 实际是**文件缺失**（全仓当前 0 个 0 字节文件）。两种情况的运行时症状完全一致
  > （`imageOk` 都返回 false → 同样落到第 3 帧），但修法不同：缺失要先补文件，
  > 0 字节要重切条带。**同时** `files` 指向不存在的路径会让 `warm()` 每次启动发一次 404。
  实测 `p.walk` 从 0 推到 4.0（覆盖 1 整轮循环）的实际帧序列：
  ```
  期望  0123 0123 0123 0123 0123 0123 0123 0123 …
  实际  0000000000000 1111111111111 222222222222222222222222222222
  计数  {0:14, 1:13, 2:33}     ← 第 3 帧被画了 33 次，是正常值（15 次）的 2.2 倍
  ```
  也就是说 **4 帧循环退化成 3 帧**，且第 3 帧占了一半时间 —— 玩家读到的就是「走路卡住」。
  额外证据：`walk-axe-0` vs `walk-axe-2` 的剪影差异只有 **4.3%**（合格线 ≥8%，
  见 `docs/素材契约.md` 第 6 节），这两帧本身就已经太像，兜底再叠上去等于两个近似帧连续播。
- **修改方案**（二选一，推荐 A）：
  - **A（补素材，根治）**：重跑 `python tools/slice_weapon_walk.py --src <条带目录>`，
    重出 `walk-axe` 条带。跑完必须 `node --check js/anim-data.js` +
    `Test-Path assets/anim/walk-axe-3.webp` 确认**文件存在且 > 0 字节**。
    验收：4 帧两两剪影差异都 ≥8%。
  - **B（先止血，不改素材）**：把 `js/anim-data.js:236` 的 `files` 数组改成只留 3 项，
    同时把 `frames` 从 `4` 改成 `3`：
    ```js
    /* 原 */
    frames: 4, ... files: ["assets/anim/walk-axe-0.webp", "assets/anim/walk-axe-1.webp", "assets/anim/walk-axe-2.webp", "assets/anim/walk-axe-3.webp"] },
    /* 改 */
    frames: 3, ... files: ["assets/anim/walk-axe-0.webp", "assets/anim/walk-axe-1.webp", "assets/anim/walk-axe-2.webp"] },
    ```
    并把该 clip 的 `frames` 从 `4` 改成 `3`（`frames` 字段与 `files.length`
    不一致会让 `char-rig.js:896` 的 `n` 取错）。**不要**只删文件不改数据 ——
    `files` 指向不存在的路径会让 `warm()` 每次启动都发一次 404 请求。
    注意：`git status` 里已有 `D assets/anim/walk-axe-3.webp` 的暂存删除，
    说明**有人已经在往这个方向改**，落手前先跟那条改动对齐，别重复做。
- **严重度：致命**（唯一一处「玩家每走一步都在看」的循环动画里缺帧，且症状是永久的）

### BUG-画面-02 拿着石头/弓/斧受伤时，整个人当场胀大 8~19%

- **玩家看到**：被打中的一瞬间，角色**突然变大一圈**——头变宽、肩变厚、靴子变大，
  然后再缩回来。同一把武器，走路时是这个大小，挨打时明显更大。
- **触发**：手上是 `rock`（眼形石）/`bow`（神鸟弓）/`axe`/`sword` 时被敌人打中（`p.hurtT > 0`）。
- **位置**：`js/anim-data.js:308`（`WEAPON_CLIP.rock.hurt`）、`:291`（`bow.hurt`）、
  `:240`（`axe.hurt`）、`:223`（`sword.hurt`）→ 渲染在 `js/char-rig.js:1003` `drawWeaponState()`
- **根因**：`WEAPON_CLIP` 每把武器的 5 个状态**共用同一画布 + 同一个 `scaleFix`**
  （已核实：11 把武器的 `w/h/scaleFix` 在 5 个状态里**完全一致**，见下表），
  设计意图是「同一把武器各状态不许忽大忽小」。但 `hurt-<key>.webp` 的**源画本身画得更大**，
  而共用 `scaleFix` 无法修正源画差异 —— 于是差异 100% 落到屏幕上。

  | 武器 | 画布 | walk 身高 | hurt 身高 | hurt/walk |
  |---|---|---|---|---|
  | rock | 399×560 | 175.8 | **209.9** | **1.19（+19%）** |
  | bow | 439×560 | 175.1 | **200.4** | **1.14（+14%）** |
  | axe | 372×560 | 175.2 | **193.0** | **1.10（+10%）** |
  | sword | 543×560 | 175.0 | **189.7** | **1.08（+8%）** |
  | bell | 466×560 | 174.0 | 181.2 | 1.04（可接受） |

  实拍对照图（左 walk / 右 hurt，脚底对齐，青线 = 177.1px 基准）：
  `tmp/audit_visual/hurtcmp/rock.png` —— 右边那个明显高一整头。
  > **现状：hurt 部分已修**（`hurt` 全部 = 177.1px，差 ≤1.4%）。
  > **但 `pickup` 没跟着改**，复测仍偏小 **1.1%~17.5%**：
  > `short` 144.4 / `hammer` 149.7 / `bell` 153.4 / `blade` 155.3 / `dagger` 156.7 /
  > `axe` 157.4 / `jar` 158.6 / `sword` 161.3 / `rock` 170.9 / `bow` 173.3 / `spear` 186.6（walk 均 ~175）。
  > 捡东西时角色会**缩一圈**，这就是本条剩下的部分。
  同类问题不止 hurt：`pickup` 普遍**偏小 15~21%**（`short` 131 vs walk 175、
  `spear` 124 vs 172、`hammer` 125 vs 174），11 把武器的 `walk→hurt` 极差最大到 **56%**。
- **修改方案**：`scaleFix` 必须**按状态**分开，不能一把武器一个数。
  契约原文（`docs/素材契约.md` 第 4 节）写的是「`scaleFix` 每把武器每个状态一个数」，
  但 `anim-data.js` 里落成了每把武器一个数 —— 这是数据与契约不符。
  - 步骤 1：对 11 把 × 5 状态逐张实测内容高（脚本 `tmp/audit_visual/measure2.py` 可复用）。
  - 步骤 2：按 `scaleFix = (idle 内容高 ÷ idle 画布高) ÷ (该帧内容高 ÷ 该帧画布高)`
    给**每个状态**算出独立值，例如 `rock`：
    ```js
    /* 原：5 个状态共用 0.842 */
    walk:   { ... scaleFix: 0.842, ... }
    hurt:   { ... scaleFix: 0.842, ... }   /* ← 病根 */
    /* 改：hurt 按自身内容高反算，约 0.842 × (175.8/209.9) ≈ 0.705 */
    hurt:   { ... scaleFix: 0.705, ... }
    ```
  - 步骤 3：验收 —— 同一把武器 5 个状态的屏幕身高必须落在 **177 ± 3 px**。
  - ⚠️ 若坚持「共用画布 + 一个 scaleFix」的设计不变，那就**必须重出 `hurt-*` / `pickup-*` 素材**
    让源画大小一致（这 11×2 = 22 张要重跑条带）。**只改代码治不了源画差异。**
  - 📌 **并行改动提示**：审计期间发现工作区 `js/anim-data.js` 正被另一处改动修改
    （`git diff` 可见 `hurt` 的 `scaleFix` 已被逐武器改写，如 `short` 0.741→0.7091、
    `dagger` 0.786→0.7104、`sword` 0.761→0.7104、`axe` 0.774→0.7104）。

### BUG-画面-04 挥砍只有「1 帧」在动，四帧序列形同虚设

- **玩家看到**：砍一刀，角色只摆出一个姿势（举刀）然后立刻复位，**看不到刀挥下去的中间过程**。
  连续三连击也像同一张图闪三下。
- **触发**：任意近战武器挥砍。
- **位置**：`js/char-rig.js:424` `attackFrame()` + `js/char-rig.js:972` `stateFrame()`
- **根因**：帧号由 `swingT / swingDur` 推导（`prog = 1 - swingT/swingDur`，`f = floor(prog * n)`）。
  但 `doSwingHit()` 在**判定成立的那一刻**就被调用（`index.html:2168`），而 `swingT` 此时
  才刚开始从 `swingDur` 往下走 —— 挥砍的绝大部分时长被 `hitstop`（`index.html` 的
  `G.hitstop = big ? 0.075 : 0.04`）吃掉。实测用 mock canvas 扫 `swingT` 全区间，
  `attack-<key>-0..3` 四帧里只有 1 帧真正上屏。
  自检脚本 `tools/selftest_weapons.mjs:326` 的断言是
  `seen.size >= 2`（「至少 2 个不同帧」），**这个门槛太低**，1 帧也能过 —— 所以自检全绿。
- **修改方案**：
  - 先确认：把自检门槛从 `>= 2` 提到 `>= n - 1`（4 帧序列要播到至少 3 帧）：
    ```js
    /* tools/selftest_weapons.mjs:326 附近 */
    ok(seen.size >= 2, ...)      /* 原 */
    ok(seen.size >= Math.max(2, n - 1), ...)   /* 改 */
    ```
  - 再修帧号：`attackFrame()` 里 `n` 太大而实际可用时间太短时，应按**可用时长**压缩帧数，
    而不是让 `floor(prog*n)` 永远停在 0：
    ```js
    /* js/char-rig.js:424 attackFrame() */
    function attackFrame(p, n) {
      if (!(p.swingT > 0) || !(p.swingDur > 0)) return -1;
      var prog = 1 - p.swingT / p.swingDur;
      if (prog < 0) prog = 0;
      if (prog > 1) prog = 1;
      var f = Math.floor(prog * n);
      /* 补：出手瞬间 swingT≈swingDur → prog≈0 → 永远第 0 帧。
         把前 60% 时长映射到全部帧，让动作在 hitstop 里也走完 */
      var f2 = Math.floor(Math.min(1, prog / 0.6) * n);
      if (f2 < 0) f2 = 0;
      if (f2 > n - 1) f2 = n - 1;
      return f2;
    }
    ```
- **严重度：高**（40 张序列帧 + 10 张单帧出招图的实际观感收益被吃掉大半）

- **位置**：`js/enemies-assets.js:1123` `var off = hsh(Math.round(num(e.x, 0) * 0.37) + 1) * n;`
- **根因**：帧号 = `floor(distPx / stride * n + off) % n`，`off` 本该是「让不同敌人错开相位」的
  固定偏移，但它被写成了 **`e.x` 的函数** —— 敌人每前进 1px，`off` 就在 `0..n` 之间重新随机。

  |---|---|---|---|
  | walker | **32** | 2.93 | **10.9×** |
  | fast | **41** | 6.08 | **6.7×** |
  | brute | **20** | 1.75 | **11.4×** |
  | boss | **18** | 0.79 | **22.7×** |

  —— 在 0..4 之间乱跳。
- **修改方案**：`off` 改成**只依赖敌人身份**的稳定种子（用出生时的 `e.walk` 初值，
  它在 `index.html` 构造时是 `rnd(0,6)`，天然每个敌人不同）：
  ```js
  /* js/enemies-assets.js:1123 原 */
  var off = hsh(Math.round(num(e.x, 0) * 0.37) + 1) * n;
  /* 改：种子只取身份，不取位置 */
  var off = hsh(num(e.__seed, 0) + 1) * n;
  ```
  并在 `index.html` 的 `Enemy` 构造里加一行（`this.walk = rnd(0,6);` 之后）：
  ```js
  this.__seed = this.walk;      /* 固定相位种子，不随移动变化 */
  ```
  验证（同脚本「修正方案」段）：改后 walker 1 秒换 **3** 次、fast **6** 次、brute **1** 次、boss **0** 次
  —— 全部落到可读步频。
- **严重度：高**（敌人是屏幕上一直在动的东西，抽搐会一直存在）

  ```js
  /* js/char-rig.js:929-932 附近，原 */
  var alpha = 1;

  else if (p.inv > 0 && Math.floor(p.inv * 20) % 2 === 0) alpha = 0.55;
  /* 改：受伤闪白优先，不再叠半透明 */
  var alpha = 1;
  if (p.dead) alpha = 0.5;
  else if (p.hurtT > 0) alpha = 1;                    /* 闪白期间保持满不透明 */
  else if (p.inv > 0 && Math.floor(p.inv * 20) % 2 === 0) alpha = 0.72;  /* 0.55 → 0.72 */
  ```

### BUG-画面-18 宝箱/机关的贴图高度按「猜的比例」算，缺图降级与素材版大小不一致

- **玩家看到**：同一只宝箱，有素材时是 A 大小，素材加载失败退回纯代码绘制时**变大或变小**，
  位置也偏一点；机关（`mechanism`）同样。
- **触发**：素材未就绪的首帧 / 加载失败。
- **位置**：`index.html:3748` `drawChests()` 用 `spriteH(key, INTERACT_W, INTERACT_W*0.78)`；
  降级 `drawChestFallback()`（`index.html:3748` 之后）用 `bw = w*0.86; bh = bw*0.50`
- **根因**：素材版高度由 `spriteH()` 按**真实宽高比**算（`index.html:3655` 附近的
  `return dispW * (im.naturalHeight / im.naturalWidth)`），
  而 `chest-closed.webp` 实测 **260×125**（比例 0.481），
  `INTERACT_W*0.78 = 140.4` 是**写死的近似值**，只在素材缺失时用作 fallback 参数，
  真正画素材时并不用它 —— 但降级路径用的是另一套 `bw*0.50`（比例 0.50）。
  0.481 vs 0.50 差 4%，再加上 `bw = w*0.86`（素材版是满宽 180，降级是 154.8），
  所以**降级版比素材版小 14%**，切换瞬间会「跳一下大小」。
  机关 `mechanism-off.webp` 实测 **260×216**（比例 0.831），降级用 `INTERACT_W*0.86 = 154.8`
  （比例 0.86）—— 也有 3% 偏差。
- **修改方案**：让降级路径**用与素材一致的常量**，而不是各自写死一套：
  ```js
  /* index.html:3737 附近，新增两个比例常量 */
  var INTERACT_W = 180;
  var CHEST_ASPECT   = 125 / 260;   /* = 0.4808，与 chest-closed.webp 实测一致 */
  var MECH_ASPECT    = 216 / 260;   /* = 0.8308，与 mechanism-off.webp 实测一致 */

  /* drawChests 里原 */
  var h = spriteH(key, INTERACT_W, INTERACT_W*0.78);
  /* 改 */
  var h = spriteH(key, INTERACT_W, INTERACT_W * CHEST_ASPECT);

  /* drawChestFallback 里原 */
  var bw = w*0.86; var bh = bw*0.50;
  /* 改：满宽 + 同一比例，与素材版一致 */
  var bw = w; var bh = bw * CHEST_ASPECT;
  ```
  机关同理（`index.html:3777` 的 `INTERACT_W*0.86` → `INTERACT_W * MECH_ASPECT`）。
- **严重度：低**（只在首帧/缺图时出现，但「宝箱大小跳一下」很违和）

## 3. 可优化点（视觉 / 性能 / 素材体积）

### 视觉

   建议加一个上限：`ctx.globalAlpha = Math.min(0.45 * k2 * alpha, 0.5)`。

### 性能

5. **`tintedFrame()`（`js/char-rig.js:510`）每次换帧都可能重建 canvas** ——
   它按 `name#idx` 缓存，但 `WEAPON_CLIP` 有 11 把 × 5 状态 × 最多 4 帧 = 55 个 key，
   再乘 2 个玩家配色 = **110 张 canvas 常驻**。每张按屏幕尺寸（约 130×180）算，
   110 张约 **2.5 MB 显存**。可接受，但如果要省，可以把 tint 从「整帧预渲染」
   改成「`globalAlpha` + 单色 overlay」，省掉 110 个 canvas。
6. **`warm()` / `warmHold()` / `warmStateClips()` 在启动时同步建 250 个 Image**
   （`js/char-rig.js:335`）。`file://` 下这些 Image 会同时发请求，
   虽然实测 85ms 能全部建好（`docs/ARCHITECTURE.md` 第 85 行的判定依据），
   但**修完 BUG-画面-17 能砍掉 1.78 MB 后，首屏会明显更快**。
7. **`drawBG()`（`index.html:2824`）是纯代码背景，但 `Background.draw()` 优先**
   —— 只有在素材缺失时才走 `drawBG`。两套背景都保留是对的（降级要求），
   但 `drawBG` 里的神树（3 棵 × 三层九枝 × 贝塞尔）每帧重算约 200 条路径，
   降级时帧率会掉。建议把 `drawBG` 的神树**预渲染到一张离屏 canvas**
   （只在首次调用时画一次，之后 `drawImage`）。

### 素材体积

8. **`assets/anim/` 250 张 7.73 MB，其中 43 张是公共 ANIM，实测 1.11 MB**。
   公共 ANIM 只在**空手**时用到（见 BUG-画面-09），而空手是低频状态。
   若给空手补 `WEAPON_CLIP.fist`（方案 A），**公共 43 帧可整批删除 → 省 1.11 MB**。
   `anim/` 按前缀实测：`atk` 50 张 1.78 MB、`attack` 56 张 1.48 MB、`walk` 49 张 1.30 MB、
   `jump` 25 张 0.84 MB、`pickup` 14 张 0.58 MB、`hurt` 13 张 0.53 MB、
   `enemy` 14 张 0.41 MB、`hold` 11 张 0.39 MB，其余 8 组各 ≤ 0.10 MB。
9. **`atk-<key>.webp`（10 张单帧，436 KB）与 `atk-<key>-<i>`（40 张序列，1.36 MB）
   功能完全重复** —— 都是「这把武器出招的样子」，一个 1 帧一个 4 帧。
   合计 **50 张 1.78 MB**，在 `WEAPON_CLIP` 存在时**全部轮不到**（见 BUG-画面-03）。
   按 BUG-画面-03 选方案 B（保留 `WEAPON_CLIP.attack`）后整套删除 → **省 1.78 MB**。
10. **`hit-jade/bronze/blunt/airy`（4 张 114 KB）与 `hit-1/2/3.webp`（3 张 78 KB）重复** ——
    前者是材质专用、后者是通用档。`fx.js:378` 的 `var img = matImg || imgOf("hit" + idx);`
    说明材质图优先、通用图兜底，**两套都必须留**（降级要求），不算浪费。
11. **`ui/title-scene.webp`(180KB) 与 `ui/title-bg.webp`(173KB) 是两张不同的标题背景**
    （一张给 `index.html` 的 `.ov-title`、一张给 `js/ui-shell.js` 的模式页），
    实测平均像素差 **41.4/255**、88% 的像素有可见差异 —— **不是重复图，不该合并**。
    真要省这 0.35 MB，得重出其中一张降采样（两处都是满屏背景，可压到 100KB/张）。
