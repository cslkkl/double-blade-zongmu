# 依据：敌人脚步为何按位移播放

状态：生效

## 背景

- 维护者反馈「小怪脚步频率太快」，可敌人移动速度本身没改过。
- 要确认步频到底跟什么走，以及改哪里才不动其它手感。

## 结论

- 原实现按真实时间推进：`Math.floor(now * fps + off) % n`，`now` 是 `G.time`（秒，由 `index.html` 的 `G.time += dt` 累加）。
- 于是步频 = `fps / 帧数`，与移动速度完全脱钩。
  - walker：4 帧 / 7fps → 每秒循环 1.75 次，速度 110px/s。
  - fast：4 帧 / 10fps → 每秒循环 2.5 次，速度 225px/s。
  - brute：4 帧 / 6fps → 每秒循环 1.5 次，速度 78px/s。
  - 速度差最大 2.9 倍（225 / 78），步频只差 1.67 倍，慢速敌人的脚步相对偏密。
- 提交 `04095d3` 改成按实际位移推进：`distPx = e.walk * 38.46`，`idx = floor(distPx / stride * n + off) % n`。
  - `e.walk` 由 `index.html` 按 `|vx| * dt * 0.026` 累加，乘 38.46（≈ 1 / 0.026）还原成像素位移。
  - `stride` 是一个完整循环覆盖的位移，写在 [js/enemies-assets.js](../../js/enemies-assets.js) 的 `STRIDE`：walker 150 / fast 148 / brute 178 / boss 240。
  - 相位 `off` 仍按 `e.x` 哈希打散，保留「同屏不同步踏步」。
- 存疑一处：提交信息记的「每秒循环 3.5 次」对应 4 帧 / 14fps，而改前数据是 7fps；`anim-data.js` 的注释「脚步已放慢」表明先前档位更高，具体旧值仓库里查不到。
- 副作用：`fps` 在 [js/enemies-assets.js](../../js/enemies-assets.js) 里已无消费方，敌人走路帧只由 `files.length` 与位移决定。

## 支撑的决策

无 —— 纯缺陷修复，没有下游决策。

## 影响

- 改速度会直接改步频，这是设计意图；想单独调步频就调 `STRIDE`，别去改 `fps`。
- `e.walk` 的累加在 `index.html`、不在渲染模块：改累加系数会同时改步频，必须同步改 `38.46`。
- 现状：累加分支带 `kind !== "boss"` 条件，BOSS 的 `e.walk` 只有构造时的 `rnd(0,6)` 初值，因此 BOSS 走路帧停在固定帧，`STRIDE.boss` 目前没有实际效果。
- `fps` 若被重新接回敌人走路，或累加系数改动，这条依据即过期。
